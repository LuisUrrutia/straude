# Straude Agent-Readiness Audit — 2026-08-21

## Executive Summary

Straude’s agent readiness is **C+ (71/100 in the supplied Ora audit)**: the site is crawlable and the production homepage already sends meaningful server-rendered content, but agents have no negotiated Markdown representation, no instruction index, and poor recovery paths. The three largest risks are cache-unsafe content negotiation once Markdown is introduced, a generic 404 that strands non-browser clients, and incomplete public trust signals. The three highest-leverage opportunities are a protocol-correct `Accept: text/markdown` path, a concise `/llms.txt` with concrete when-to-use guidance, and substantive About/Contact pages connected through the sitemap and footer. The supplied “no H1” finding is not reproducible against the current deployment: the raw August 21 response contains one `<h1>` and more than 4,200 visible characters. Content efficiency remains just below the audit threshold at roughly 4.05%, so the implementation should improve the agent representation without destabilizing the existing landing design. Organization schema can safely publish the established `hey@straude.com` support address and a country-level postal address, but a phone number or street address must not be invented. The implementation is bounded, testable, and should clear 90 if the failed and partial protocol checks become full credit.

## Repo Map

Straude is a production Bun/Turborepo application: Next.js 16 and React 19 power the web app, the CLI is a TypeScript package, and Supabase supplies authentication and data. The public landing route is a cached server component with small interactive client islands.

```text
request
  -> apps/web/proxy.ts
     -> lib/supabase/middleware.ts (session refresh and auth redirects)
        -> Next App Router page or route handler
           -> landing server components + small client islands
```

- `apps/web/app/`: App Router pages, API handlers, sitemap, robots, and global metadata.
- `apps/web/components/landing/`: the public visual system and landing content.
- `apps/web/lib/supabase/middleware.ts`: request/session behavior composed by `proxy.ts`.
- `apps/web/__tests__/`: Vitest behavior tests.
- `apps/web/e2e/`: Playwright production-server checks.
- `docs/`: operational, architecture, and decision records.

The relevant conventions are explicit in `CLAUDE.md`: use `proxy.ts` for Next 16, preserve deterministic SSR, reuse the landing design system, and record material changes in `docs/CHANGELOG.md` and `docs/DECISIONS.md`.

## Audit Report

### Critical and high findings

1. **High — Markdown negotiation is absent (fact).** `apps/web/proxy.ts:1-6` only delegates to the Supabase session middleware, and `apps/web/next.config.ts:38-83` configures security headers without `Accept` variation. A live request with `Accept: text/markdown` returned `text/html` and omitted `Accept` from `Vary`. This is both the supplied audit’s only outright Essential failure and a cache correctness risk once variants exist.
2. **High — The 404 representation has no recovery path (fact).** There is no `apps/web/app/not-found.tsx`; the live 404 is Next’s generic 92-character message. Although the HTTP status is correctly 404, agents receive no link to the homepage, sitemap, or future `/llms.txt`.

### Medium findings

3. **Medium — No agent instruction index exists (fact).** `/llms.txt` returns 404 and no equivalent file is present. Agents cannot cheaply identify Straude’s best-fit jobs or canonical surfaces.
4. **Medium — Trust pages are incomplete (fact).** `/privacy` is substantive at `apps/web/app/(landing)/privacy/page.tsx:11-218`, but `/about` and `/contact` do not exist. `apps/web/app/sitemap.ts:15-23` and `apps/web/components/landing/Footer.tsx:25-55` therefore cannot expose them.
5. **Medium — Organization schema omits contact and address (fact).** The global Organization JSON-LD at `apps/web/app/layout.tsx:96-110` includes name, URL, logo, description, and GitHub, but no `contactPoint` or `address`.
6. **Medium — Homepage content efficiency is below the supplied 5% target (fact).** The August 21 production response was 104,283 bytes with approximately 4,220 visible characters after excluding scripts and styles (about 4.05%). App Router hydration data accounts for much of the difference.

### Corrected supplied finding

7. **No current SSR failure reproduced (fact).** `apps/web/app/(landing)/page.tsx:74-117` renders the landing tree as a server component, and `apps/web/components/landing/Hero.tsx:19-23` contains the H1. The live raw HTML contained one H1 and more than 500 characters without executing JavaScript. **Judgment:** preserve this architecture and add a wire-level regression test rather than refactoring SSR that already works.

### Strengths to preserve

- The homepage already uses server components with isolated client behavior, avoiding a broad client-only shell.
- Unknown paths already return a real 404 status.
- `/privacy`, `/robots.txt`, and `/sitemap.xml` are public and substantive.
- Security headers are centralized, and the existing test stack supports unit, production-server, and browser verification.
- The user-facing landing voice and visual system are consistent and should be reused for trust and recovery pages.

## Improvement Strategy

### Theme 1 — Negotiate representations at the request boundary

**Target state:** q-value-aware negotiation runs only for safe document requests, rewrites known public pages to a curated Markdown handler, and leaves API/auth behavior unchanged. Every negotiated response carries `Vary: Accept, Accept-Encoding`.

**Principle:** representation selection and cache identity belong at the shared request boundary, not inside individual React pages.

### Theme 2 — Give agents an explicit map and recovery path

**Target state:** `/llms.txt` follows the llmstxt proposal, names concrete use cases, and links to canonical pages; both HTML and Markdown 404s return status 404 with useful recovery links.

**Principle:** failure responses should tell an autonomous client how to recover.

### Theme 3 — Make public trust claims verifiable

**Target state:** About, Contact, and Privacy are substantive, indexed, internally linked pages; Organization JSON-LD reflects only public facts.

**Principle:** structured data must mirror real, visible content and must never invent contact details.

### Trade-offs

- Do not convert rendered HTML to Markdown at request time. It would double-render, complicate auth and recursion, and risk leaking personalized output.
- Do not replace the landing page or remove its interactive islands solely to chase the HTML ratio. A curated agent representation and modest semantic improvements have lower product risk.
- Do not publish a telephone number or street address without a real public business value. Country-only `PostalAddress` is honest but may remain partial in stricter validators.

### Definition of done

- `Accept: text/markdown` on supported public pages returns `200`, Markdown content type, meaningful content, and cache-safe `Vary`.
- HTML requests still return the existing design, auth redirects, and hydration behavior.
- Unknown HTML and Markdown requests both return true 404 responses with recovery links.
- `/llms.txt`, `/about`, `/contact`, `/privacy`, `/sitemap.xml`, and `/robots.txt` are reachable and verified.
- Raw homepage HTML contains exactly one H1 and more than 500 visible characters without JavaScript.
- Unit tests, focused Playwright checks, lint, typecheck, and production build pass.
- A rerun of the readiness audit or equivalent endpoint matrix demonstrates at least 90/100 before the PR is considered complete.

### Quick wins

- Add `/about` and `/contact` to the sitemap and footer.
- Add a custom semantic 404 with recovery links.
- Publish `hey@straude.com` as the established customer-support contact.
- Add a wire-level H1/body-length regression test so the stale SSR finding cannot recur silently.

### Implementation sketches for the top tasks

1. **Negotiation:** keep `proxy.ts` as the composition point; use a pure parser/classifier, rewrite supported document requests to an internal Markdown handler, and append cache variation without overwriting Next tokens. Bypass APIs, assets, RSC requests, and non-GET/HEAD methods.
2. **Agent content and 404:** store curated Markdown in a small shared content module. Serve known documents from one internal handler and an uncached recovery document for unknown Markdown paths. Render the HTML 404 with existing Navbar/Footer components and native links.
3. **Trust surface:** add server-rendered About and Contact pages using the privacy page’s layout, deterministic Next metadata, and visible claims that match JSON-LD. Link them from the footer, sitemap, llms.txt, and 404.

## Verification Result

The live `straude.com` baseline was re-fetched from Ora before implementation and confirmed the supplied Essentials score of **71**. On 2026-08-21, the completed production build was exposed through a short-lived public tunnel and submitted to Ora as an ephemeral scan. It scored **90 Essentials** with the label **Strong technical baseline**. Markdown negotiation with `Vary: Accept`, the recovery-oriented 404, agent instructions, Organization schema completeness, and all three trust anchors received full credit. The tunnel was removed after the scan; production remains unchanged until this branch is reviewed and deployed.

- The supplied Ora audit appears stale on H1/SSR. If its production scanner still reports the same failure after deployment, its user agent and extraction method will need inspection rather than another blind rendering refactor.
